# Core 09 — UI shell: Dear ImGui

*Modernizes M05-F03 (ribbon/browser/docking) and the interaction/selection pipeline
(M05-F04). Implements ADR-0004. Borrows realtime-3d §10 (reflection-driven property
editing) and §12 (one-window, no OS popups).*

> **Ribbon layout is specified by [../mapping/inventor-ribbon-structure.md](../mapping/inventor-ribbon-structure.md)**
> — the canonical tab→panel→button tree Oblikovati mirrors from Inventor. The ribbon is
> *generated* from the command registry (below), but every command's tab/panel placement
> must follow that document.

## Split of responsibilities

- **ImGui owns the chrome**: ribbon/toolbars, browser tree, parameter table,
  property/inspector panels, dialogs, BOM/parts tables, toasts. Built with
  **cimgui-go**, docking branch, rendered last in the Vulkan frame (core/08).
- **The viewport owns 3D**: rendering, picking (ID buffer), drag manipulators,
  rubber-band selection, snapping previews. **Not** ImGui.
- They meet only through the **runtime mediator**, the **selection**, the
  **command** system, and the **registries** — ImGui never touches Vulkan handles;
  the viewport never hardcodes panel layout (the boundary from ADR-0004).

## The shell is built from model state each frame

Immediate mode: phase 8 (core/00) walks current model state and emits widgets. No
retained UI tree to keep in sync — the model *is* the state (which is *more*
aligned with "logic in compiled code" than the COM browser's parallel node tree).

```
ui phase:
  ribbon:   for cmd in registry.Commands by category: imgui.Button(cmd.Meta) → cmd.Run on click
  browser:  walk active document: features / parameters / occurrences → tree nodes
  inspector:for the selected feature: reflect its Definition struct → property widgets
  panels:   parameters table, BOM, messages — all read live model, write via commands
```

### Ribbon/commands from the registry

The ribbon is generated by reading `registry.Commands` (core/07) — tab → panel →
button, with `Meta().EnablePredicate` driving greying. Adding a command (a package +
one import) makes a button appear with **no UI code edited**. This replaces the COM
`CommandManager`/`ControlDefinitions`/`CommandBars` machinery with "registry → widgets."

**One ribbon per document type, switched by context** (Inventor's RibbonUI model — see
`Inventor-API/files/RibbonUI_Overview.md`). There is a ribbon per document type plus
`ZeroDoc` (no document open): `ZeroDoc, Part, Assembly, Drawing, Presentation, iFeatures,
UnknownDocument`, keyed by `RibbonKey`. Each command declares the ribbon(s) it belongs to
(`WithRibbons`, default `Part`) and an `Environment` (`WithEnvironment`, default base).
`BuildRibbon` picks the ribbon for the active document (`ribbonKeyForDocument`, `ZeroDoc`
when none open) and includes only the commands scoped to that ribbon **and** the current
environment — so the **Sketch tab is contextual**, present only while a sketch is open, and
opening a part flips the whole ribbon from ZeroDoc (Get Started) to Part. Greying via the
enable predicate is for *temporarily-unavailable* commands within the active ribbon, not for
hiding another document type's commands.

### Browser from the live document

The browser tree reflects the document's feature history, parameters, sketches, and
(for assemblies) the occurrence tree — read directly from the model each frame.
Node actions (rename, suppress, delete, reorder) issue **commands** (core/06), so
they are undoable for free. Replaces COM `BrowserPane`/`BrowserNode` retained nodes.

## Reflection-driven inspector (realtime-3d §10)

The biggest leverage point. Every feature carries a `Definition` struct (the
triangle, parametric-cad §3). The inspector **reflects over that struct + field
tags** to auto-generate its edit panel — one code path edits *every* feature type:

```go
type ExtrudeDefinition struct {
    Distance param.Quantity `label:"Distance" unit:"length" min:"0"`
    Taper    param.Quantity `label:"Taper" unit:"angle"`
    Operation OpKind        `label:"Operation" enum:"join,cut,intersect,newbody"`
    Symmetric bool          `label:"Symmetric"`
    Profile  Ref            `label:"Profile" pick:"profile"`
}
```

- Tags declare **intent** (label, unit, clamp, enum choices, pick-filter, visibility)
  exactly like realtime-3d §10.
- Editing a field builds an `EditDefinition` **command** → async recompute (ADR-0007).
- Constrain editable fields to plain-old-data + `Quantity` + `Ref` so generation is
  total. New feature → define its `Definition` struct → its panel exists for free.

This is the modern realization of "construct-then-create": the same `Definition`
struct is the create dialog, the edit panel, the serialized record, and (as a
protobuf message) the gRPC `Edit` payload — one representation, four uses.

## Interaction & selection (viewport side)

- **Picking** reads the ID-buffer pixel under the cursor (core/08) → exact selection
  honoring the active **selection filter** (faces/edges/features/occurrences).
  Replaces COM `HitTestManager`/`SelectionFilterEnum`.
- **SelectSet** is a `*Selection` on the runtime: `[]Entity`, change-eventing
  (core/06), shared by viewport and ImGui (the inspector reflects whatever is
  selected).
- **Manipulators** (drag handles, the move triad, dimension drags) are viewport
  overlays driven by the interaction phase; their commit is a command.
- **Snapping/preview** uses the overlay (client-graphics) pass — the same surface
  add-ins draw into (core/07).

## One window, no OS popups (realtime-3d §12)

Confirmations, progress, file pickers, and prompts are **in-window ImGui modals/
overlays** that block input to the rest of the app — one cohesive window, not a
constellation of OS dialogs. A **project/document context** is required before the
tool is fully usable (a start screen forces document selection), matching the
skill's tooling-UX guidance and the COM environment model.

## Why this is enough despite diverging from the skill's §8

ADR-0004 accepts immediate-mode for the chrome. The skill's retained-mode/dirty-flag
machinery is still used where it pays — the **viewport** scene graph (core/08). The
chrome is bounded (a few dozen widgets; the 3D view dominates frame cost), state
lives in the model not the UI, and the reflection-inspector keeps per-type UI glue
at zero. If a bespoke product shell is ever wanted, the strict model/command/registry
separation means it can be reskinned without touching domain code.
