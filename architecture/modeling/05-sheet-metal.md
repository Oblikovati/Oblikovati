# Modeling 05 — Sheet metal

*Modernizes M13 (sheet-metal environment, wall/bend features, modify, flat pattern).
Architecturally: a **specialized part environment** (a rule-driven flavor of part
content) plus a derived **flat-pattern model** — both expressed with the existing
feature engine (modeling/01), no new core machinery.*

## Sheet metal is a part content flavor, not a new document type

A sheet-metal part is a `PartContent` (modeling/01) with a **rule set** attached and
a **sheet-metal feature registry** active (the "environment" — a registered
`Workspace`, core/07). It is not a separate document kind; it is the same content
with extra invariants (constant thickness) and an extra feature family.

```go
type SheetMetalContent struct {
    *compdef.PartContent              // it IS a part (features, params, bodies…)
    rule    SheetMetalRule            // active style: thickness, bend radius, relief, gap
    unfold  UnfoldMethod              // K-factor | bend table | custom equation
    flat    *FlatPattern             // derived; nil until generated
}
type SheetMetalRule struct {
    Thickness   param.Quantity        // ← a parameter: every wall honors it
    BendRadius  param.Quantity
    KFactor     float64
    Relief      ReliefStyle
}
```

- The **rule is parameter-backed** (core/04): changing thickness recomputes every
  wall/bend through the normal feature engine. Rules are styles (shareable,
  library-managed — visualization iteration covers styles, M16).
- The **active environment** swaps the ribbon to sheet-metal commands (registry →
  ImGui, core/09) — the COM `Environment` concept as a registered workspace.

## Wall & bend features — the same triangle

Each is a `Feature` with a `Definition`, calling kernel ops, honoring the rule:

| Feature | Definition highlights | Phase |
|---|---|---|
| **Face** (base/secondary) | `Profile Ref`, thickness from rule | A |
| **Flange** | edge `[]Ref`, angle, height, bend from rule | A/B |
| **Contour flange** | open `Profile Ref` swept along edges | B |
| **Hem / Bend / Fold** | edge/sketch-line `Ref`, type, radius from rule | A/B |
| **Corner** (chamfer/round/seam) | corner `Ref`, treatment | A |
| **Lofted flange / Contour roll** | two profiles / profile + axis | B/C |

The defining extra requirement: **every bend records its unfold parameters**
(neutral-axis position from K-factor, bend allowance) as lineage/attributes, because
the flat pattern needs them. This is just more lineage on the result topology
(core/03) — the reference-key machinery already carries it.

## Modify features

Cut (with across-bend unfolding), Rip, Lip, Punch (iFeature-driven), Cosmetic bend,
Corner seam — same triangle. **Cut-across-bends** is the interesting one: it must
unfold the affected region, cut in flat space, and refold — implemented as the op
consulting the bend lineage, not as a special engine path.

## The flat pattern is a derived model

The flat pattern is a **derived body computed from the folded model** — conceptually
like a derived part (modeling/02): an associative output that recomputes when the
folded part changes.

```go
type FlatPattern struct {
    body     *topo.Body          // the developed flat
    bends    []BendLine          // bend lines + angles + allowances
    extents  math.Box2d
    punches  []PunchToken        // punch representations for export
}
func (c *SheetMetalContent) Unfold() *FlatPattern   // develop using rule + per-bend lineage
```

- **Unfold/refold** are bidirectional: the flat is generated by walking the bend
  graph and developing each face into the plane using its recorded bend allowance
  (K-factor / bend table). Refold maps flat edits back.
- The flat **recomputes via the same engine** when the folded model or the rule
  changes (a parameter edit to thickness/K-factor changes flat extents) — it is a
  dependent in the DAG (core/04), rebuilt async (ADR-0007).
- **Export to DXF/DWG** (geometry + bend lines + punch tokens on layers) flows
  through the translator framework (iteration 4, M17) — the flat is just a body +
  annotations to serialize.

## Why no new architecture

Sheet metal reuses *everything*: it is a part content (feature engine), its rule is a
parameter set (DAG), its environment is a registered workspace (registry), its
features are triangles (modeling/01), its flat pattern is a DAG-dependent derived
body (async recompute), and its export is a translator. The only sheet-metal-specific
substance is **kernel/geometry work** — bend development math and across-bend cuts —
which lives in `kernel/ops/sheetmetal`, gated by kernel phase like everything else.
This is the payoff of the iteration-1/2 spine: a whole "environment" is mostly
configuration + a feature family, not new plumbing.
