# Apps 01 — Design automation: iPart & iLogic

*Modernizes M15 (iPart/iAssembly factories, embedded tables, iLogic rules, content
center). Implements ADR-0013 (embedded scripting). Design automation is almost
entirely a **client of the public API** — its purpose is to validate the surface.*

Two complementary mechanisms drive the same parameter/feature/document API: a
**declarative** one (iPart member tables) and an **imperative** one (iLogic rules).

## iPart / iAssembly factories — declarative member generation

A factory turns a part/assembly into a **family**: a table of members (rows) where
columns control parameters, feature suppression, properties, and (for assemblies)
component selection. A member is generated by **setting the row's values and
recomputing** — pure reuse of the feature engine (modeling/01).

```go
package automation
type Factory struct {
    table   MemberTable           // rows × columns (params | suppress | props | components)
    keyCols []ColumnID            // identify a member
    cache   map[MemberKey]*doc.Document   // generated members (idempotent, like a resource cache)
}
func (f *Factory) Generate(key MemberKey) (*doc.Document, error) {
    // apply the row: set parameters (core/04), suppress features (modeling/01), set props (core/05)
    // → async recompute (ADR-0007) → a concrete member document
}
```

- **No new modeling** — generation is "set inputs, recompute," the engine we already
  have. Custom (per-member) overrides persist on the generated member.
- **iFeatures** (extractable feature templates, also used by sheet-metal punches,
  modeling/05) are the feature-level analogue: a parameterized feature group placed
  into another part with value mapping.
- Member generation is cached/idempotent like the renderer's resource caches (core/08,
  realtime-3d §5) — ask the factory, get a shared member, never regenerate.

## iLogic rules — imperative automation (ADR-0013)

Rules are user-authored scripts in an **embedded sandboxed runtime** (Starlark/Lua,
pure Go) that drive the **same public API** (`/api`) as add-ins (ADR-0018), triggered
by the **event bus** (core/06):

```go
type Rule struct{ name, source string; triggers []event.TypeID }
// script globals = the public model API: parameters, features, components, selection
```

- **Triggers**: a rule fires on `parameter-changed`, `feature-added`, `before-save`,
  etc. (core/06). Rule edits go through **commands** (core/06) → undoable, and through
  **async recompute** (ADR-0007).
- **Ordering & cycles**: rules declare inputs/outputs and join the **dependency DAG**
  (core/04) — the engine topologically orders rule execution and rejects cycles (rule
  health sick), exactly like parameters. No ad-hoc "rule ran in the wrong order" bugs.
- **Forms**: a rule's user inputs are an ImGui form (core/09) — compiled UI, scripted
  logic (the ADR-0013 split: UI stays compiled, automation is scripted).
- **Sandboxed**: a rule reaches only the model API — never the renderer, UI internals,
  filesystem, or network (ADR-0013). Safe by construction.

## Content center — a library of factories

The standard-parts library (fasteners, steel shapes) is a set of **iPart factories**
backed by a family library; placing a standard part is "generate the member from the
library factory" — reusing the factory machinery above. Library/template/design-data
paths reuse the project search-path config (core/05).

## Why this milestone is mostly "free"

Design automation adds **one runtime** (the rules interpreter, ADR-0013) and is
otherwise a **client** of mechanisms already built: parameters (core/04), the feature
engine (modeling/01), documents/properties (core/05), commands/events (core/06), and
ImGui forms (core/09). That is by design — and it is the **dogfood validation**
(realtime-3d §12, core/07): if user rules and member tables can fully reconfigure a
model through the public API, the public API (the in-proc `api/contract` surface *and*
its `api/wire` twin, ADR-0018) is provably complete. Design automation is where the API earns its
"complete automation surface" claim — the same aspiration the original
`Oblikovati.Contracts` had for the COM type library, now continuously tested.

## Net mapping from COM

| COM | Here |
|---|---|
| `iPartFactory`/`iAssemblyFactory` + table | `Factory` over the feature engine; cached members |
| `iFeature` | extractable parameterized feature group |
| iLogic rules | embedded Starlark/Lua over the public API (ADR-0013) |
| rule triggers | event-bus subscriptions (core/06) |
| rule forms | ImGui forms (core/09) |
| Content Center | library of `Factory`s |
