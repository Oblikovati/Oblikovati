# Rust project implementation

## Project configuration files — partial R2

Tracking: [#3695](https://github.com/Oblikovati/Oblikovati/issues/3695).
`ProjectConfiguration` reads and writes Go schema-1 `.opj` files, retaining name,
workspace, ordered libraries, templates, and design-data locations. The committed
fixture was generated by Go `WriteProjectFile` at baseline
`aa8297d1b0ac33c024f19e54821536d76e8a447a`.

Read/write require the canonical API project extension, case-insensitively.
Writes use the shared atomic replacement boundary. Unknown fields, duplicate
keys, unsupported/missing schemas, malformed field types, empty library entries,
and NUL-containing locations are refused. This is stricter than Go's permissive
field decoding and prevents silent loss of unsupported project settings.

Binding requires an explicit absolute project-file path. Relative roots resolve
against its parent; absolute roots remain absolute, and absent locations remain
unconfigured. The resulting lookup reuses workspace/library order and template
selection. Binding does not alter the portable configuration saved to disk.
Tests cover Go round trips, malformed records, relative/absolute roots, extension
checks before I/O, read failures, atomic commit failure, and native loaded-project
attachment/template lookup. Active project selection in host startup is pending.

## Active project ownership — partial R2

Tracking: [#3696](https://github.com/Oblikovati/Oblikovati/issues/3696).
`FileWorkspace` now owns validated project configurations and bound locations.
Projects register in load order under canonical paths; aliases share one owner.
The first successfully loaded project is selected automatically. Later loads
preserve that selection. Selection accepts only a registered canonical path.
Failed reads, decoding, and unknown selections leave registration and selection
unchanged. Repeated loads retain the existing configuration without reading it
again; explicit project reload is not implemented.

Selected-project reference resolution and template creation use the existing
lookup and template pipelines. The typed file host also applies the selected
project to attachment capture and discovery through the injected foreign-file
provider. Switching projects changes resolution without rewriting stored
references or touching document focus/history. No provider still means unknown
attachment status; project selection does not create hidden native I/O.

Tests cover first selection, switching, aliases, duplicate loads, failed loads,
unknown selection, reference/template behavior, and typed attachment results.
Project selection UI, startup configuration, and project wire methods remain
pending; the file-owner methods are ready for those host consumers.
